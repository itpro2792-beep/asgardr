Dead-man switch → phone

A cluster CronJob pings a receiver every 60 seconds. If the pings stop for 180, the receiver pages an Alertmanager-to-Telegram bridge and the alert lands on my phone. The cluster tells me when it's in trouble.

Self-healing failover

A manual chaos run deleted one gateway pod and watched the service. In-flight requests never dropped, and Kubernetes restored the deployment to two replicas — pod-level failover, proven by hand. The scheduled weekly version is armed but hasn't fired on its own yet.

05

What It Isn't (Yet)

The same discipline that verifies the wins names the gaps. A platform you can trust is one whose limits are stated out loud.

  • Five k3s nodes on a ten-machine fleet. The Kubernetes cluster is 5 active nodes; the other five machines are on the private mesh (all online at last check) but not joined to Kubernetes — several by design.
  • Failover is proven at the pod level, not the node level. The chaos run killed a gateway pod, not a whole machine; whole-node failure isn't claimed until it's actually tested.
  • GitOps tracks drift; it doesn't auto-correct it yet. ArgoCD reports live resources as OutOfSync against git — reconciliation is observed, not yet enforced.
  • Backup ≠ proven recovery. Backups run and complete on schedule; a full restore drill is documented but not yet independently timed here.
  • The scheduled weekly chaos test has a passing manual run, not an automatic one — the job is armed but hasn't fired on its own cadence.
  • The fine-tune's 33/50 is an internal benchmark. The next validation is a controlled base-vs-tuned A/B on unseen questions, same system prompt on both sides, independently scored.
  • The retrieval corpus is small by choice — ingestion is gated on human review, so the knowledge base grows slowly and deliberately.
