A document assistant that never sends your documents anywhere

Upload site surveys, contracts, and operations manuals. Ask questions in plain language. Get answers that quote the passage they came from. Every model call runs on hardware I own — nothing leaves the network.

Why this shape

Plenty of tools will answer questions about your documents. Most of them require handing those documents to somebody else's servers. For a venue operator holding signed service agreements, or a contractor holding as-built records and safety procedures, that is often the end of the conversation.

This runs on a private Kubernetes cluster: a vector database for retrieval, a local model gateway for inference, and a web interface. The document text is embedded locally, stored locally, and answered locally. There is no third-party API key anywhere in the request path, which means there is no version of this where a contract leaks because a vendor changed their data-retention policy.

What is the parking garage clearance height?

I'm sorry, but the uploaded document(s) do not contain sufficient information to answer your question.

No citation returned — the corpus is silent on this

The fourth answer is the important one. A document assistant that invents a clearance height is worse than no assistant, because you would act on it. Refusing cleanly when the documents do not cover the question is a feature that has to be built and tested for, not a behaviour you get for free.

How I know it works

This is the part I would want to read if I were hiring.

The project arrived with a passing test suite. The suite asked the system about OAuth2 with SAML2 fallback, AES-256-GCM encryption at rest, and a 15-minute incident response SLA — then asserted the answer was non-empty. Every one of those is answerable from a language model's general knowledge. The test passed with the vector database switched off. It was measuring nothing, and it had already been reported as proof that the system worked.

The replacement uses facts that exist in no training corpus — an asset tag, a path loss coefficient to four decimal places, a named engineer — and asserts the exact string appears in the answer. It also does three things the original did not:

  • A negative control. Ask for a fact the documents do not contain. The answer must be a refusal, not a plausible number.
  • A scoping check. Ask for document A's fact while the query is restricted to document B. A's value must not appear, and A must not be cited.
  • A failure check. Point the suite at a dead endpoint and confirm it reports the failure and exits non-zero. The original could not: a shell assignment under set -e made its entire diagnostic branch unreachable.

Things that were quietly wrong

Found by reading artifacts rather than status fields. Each of these reported healthy.

ReportedActual
Document list workingTwo replicas each cached their own list in process memory and never re-read the database. The store held 23 documents; one replica reported 6, the other 17, alternating as the load balancer rotated. Neither was correct.
Model configured correctlyThe fallback chain hardcoded a specific model ahead of the configured one, so the configured model had never once been used.
Credential managedAn API key sat as a literal default in application source, and in the built container image. Moved to a secret reference; the running image now greps clean.
Answers groundedThe grounding prompt forbade "extrapolation" so strictly that the model refused a safety question while holding the answering passage at retrieval rank 1. Retrieval was correct; the instruction was wrong.
Backup presentA backup that has never been restored is a file of unknown provenance. The restore path now runs as a drill: snapshot, restore into a scratch collection, then query the restored copy and check the answer.

The through-line: a check whose passing condition is also satisfied by the failure mode is decoration. Green is not evidence. The artifact is.
